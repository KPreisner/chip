CHIP: Confounding Hash Iteration for Passwords

CHIP hashes a salted password over and over until the low b bits of the digests have repeated C times. A salt whose chain runs past the upper bound is rejected and replaced. This page runs the real Python library in your browser; nothing you type leaves this page.

1. Why password hashes are slow on purpose

  
A stolen password database is attacked offline, so the only defense left is
    making each guess expensive.

  
A website never needs your password itself, only a way to check it. So it stores a
    hash of the password: a fixed-size fingerprint that is easy to compute
    and practically impossible to reverse. At login it hashes what you typed and compares.

  
If the database leaks, the attacker has the hashes. They can't reverse them, but they can
    guess: hash "123456", "password", "hunter2", … and look for a match. Nobody
    can rate-limit this; it runs on the attacker's own hardware. Each guess costs one run of the
    password hash, so the cost of one hash is the cost of one guess.

  
General-purpose hashes such as SHA-256 are designed to be fast: one high-end gaming GPU (an
    RTX 4090) computes about 21 billion SHA-256 hashes per second in
    hashcat's benchmark. That is good for checking files and bad for passwords. A
    password hash deliberately makes each run expensive.


  
Salts: the same password, different hashes

  
A salt is a random value stored next to each hash and mixed into it.
    Without one, everyone who chose "hunter2" has the same hash, so the attacker cracks them all
    at once, or looks the hash up in a precomputed table. With a salt, each user's hash has to
    be attacked separately. A salt does not make a single guess any slower. Making each
    guess slower is what the rest of this page is about.

  

    

    

      
      
    

  

  


  
  

  
2. What the Password Hashing Competition asked for

  
Make each guess cost time, memory, or an unpredictable amount of time.
    CHIP tries all three.

  
From 2013 to 2015 the Password Hashing
    Competition (PHC) collected new designs; Argon2 won. The entries
    use three levers, often together:

  
    
    
  • More iterations. Hash many times in a row. Simple, but an attacker with
      a GPU runs thousands of guesses side by side.
    • 
    
  • More memory. GPUs and custom chips have thousands of cores but little
      fast memory per core. If each guess needs megabytes, far fewer guesses fit at once.
    • 
    
  • Unpredictable run time. A GPU runs threads in
      lockstep groups of 32. If guesses take different amounts of time,
      the fast ones sit idle until the slowest in their group finishes.
    • 
  

  
CHIP's run time is set by when random collisions happen (section 4), so it varies from guess
    to guess. Below, each bar is one password guess on one GPU lane, with its length taken from
    real CHIP chains at the defaults. A group of 32 starts together and can't move on until its
    slowest guess is done. Watch the grey: that is time lanes spend waiting.

  

    
    

    

  

  
That waiting is the cost CHIP's variable run time adds for a GPU attacker. Each lever turns
    out weaker than it first looks; section 9 shows how an attacker gets
    this one back.

  


  
  

  
3. Digests and low bits

  
A digest is 256 random-looking bits; CHIP looks only at the last b of
    them.

  
SHA-256 turns any input into a 32-byte (256-bit) digest, usually
    written as 64 hex digits. Change one character of the input and the whole digest changes,
    with no visible pattern. So its bits behave like coin flips.

  
CHIP reads only the low b bits: the last b bits of the digest, read as a
    number. We'll write this as:

  
low_b_bits(h) = h mod 2^b        # keep only the last b bits

  
There are only 2b possible values, so they repeat far sooner than whole digests
    ever would.

  

    

    

      
      
    

  

  


  
  

  
4. The birthday paradox

  
Among 2b possible values, a repeat shows up after about
    √(2b) tries, not 2b.

  
In a room of 23 people, there is a better than even chance that two share a birthday, even
    though there are 365 days. The reason is pairs: 23 people make 23 × 22 / 2 = 253 pairs, and
    each pair has a 1 in 365 chance of matching. The number of pairs grows like the square of the
    number of people, so matches arrive much sooner than intuition says.

  
The same happens with b-bit values. Drawing random values into 2b boxes, the
    first collision (a value that was already drawn) comes after
    about

  
√(π/2 · 2^b) ≈ 1.25 · 2^(b/2) draws

  
At b = 32 that is about 82,000 draws out of 4.3 billion possible values, and the benchmark
    measured 81,000.

  

    
    

    

    

      
      
      
    

    
    

  


  
A rule of thumb for C collisions

  
CHIP waits for C collisions, not one. After T draws there are about T²/2 pairs, and each
    matches with probability 1/2b, so the expected number of collisions is about
    T² / (2 · 2b). Setting that equal to C and solving for T:

  
T ≈ √(2 · C · 2^b)

  
This one formula explains how both parameters behave:

  
    
    
  • Each extra bit multiplies the work by √2 ≈ 1.41, because doubling
      2b multiplies its square root by √2.
    • 
    
  • More collisions add work with diminishing returns, because T grows like
      √C: 4 times the collisions only doubles the iterations.
    • 
  

  
Against the measured means it is within about 4% for C ≥ 5 (b = 32, C = 5: predicted
    207,000, measured 200,000). It overestimates for C = 1 by about 15%, where the exact
    √(π/2 · 2b) above applies.

  


  
  

  
5. The CHIP chain, step by step

  
Hash, check the low bits, remember the digest or perturb with the earlier
    one, repeat until C collisions, then hash once more.

  
h = salt ‖ password
repeat:
    h = SHA256(h)                       # this is Di
    if low_b_bits(h) was seen before (as the low bits of Dj):
        collisions += 1
        h = h XOR Dj                    # perturb with the earlier full digest
    else:
        remember h under its low b bits
until collisions == C
return salt, SHA256(h)

  
Names used from here on: Di is the digest produced at iteration i; its low
    b bits are Li. A collision is an iteration whose Li equals
    the low bits of an earlier, remembered digest Dj. CHIP stores each remembered digest in a
    table keyed by its low bits. Step through a real chain, small enough to see every
    iteration:

Each box in the grid is one possible low-bit value, and shows the iteration whose digest it
    holds. Two details to notice:

  
    
    
  • The first iteration can never collide, because nothing has been remembered yet. That is
      why max_iterations must be greater than C.
    • 
    
  • After the last collision CHIP hashes once more, so the final XOR affects the output.
    • 
  

  
This is the "confounding" in CHIP's name. The number of iterations depends on exactly when
    each collision lands, and the only way to find out is to run the chain. Change one character
    of the password or salt and every digest changes, so every collision moves. Press
    New salt above to see it.

  


  
  

  
6. Why the XOR forces memory

  
XOR-ing in the full earlier digest means the hasher must be able to
    get Dj back, so it has to keep the chain's digests (or recompute them).

  
Think like an attacker checking one guess against a stolen hash, and ask what they could
    skip. Compare three versions of what a collision does:

  

    

      
      
      
    

    

  

  
    
    
  • No perturbation: the chain is just SHA-256 applied over and over;
      collisions only decide where it stops. The attacker doesn't care where: they hash, check
      the result against the stolen hash, and repeat. No memory at all.
    • 
    
  • Flip one bit: now the chain changes at each collision, so the attacker
      must notice collisions, which means remembering every low-bit value seen. That is b bits per
      iteration.
    • 
    
  • XOR with Dj: the chain depends on the other 224 bits of the earlier
      digest too, so the attacker must be able to produce any earlier digest on demand. Keeping
      them all is 32 bytes per iteration, eight times the previous row at b = 32.
    • 
  

  
Whatever is kept belongs to one password and salt, so it can't be shared between guesses.
    Keeping every digest is not the only way to get Dj back, though; section
    9 shows a cheaper one.

  


  
  

  
7. Salts, bounds, and retries

  
Chain lengths vary a lot, so CHIP throws away a salt whose chain runs too
    long and tries a new one.

  
At the defaults (b = 32, C = 5), a chain takes about 200,000 iterations on average, with a
    standard deviation of about 45,000. Some salts would take far longer. So CHIP sets an
    upper bound: if a chain hasn't reached C collisions by then, it draws a new
    salt and starts again from scratch. The red bars in the demo above are exactly these rejected
    salts. An optional lower bound (off by default) works the same way, so no
    password ends up with a suspiciously cheap hash.

  
The demo at the top starts at b = 20, about 3,000 iterations, so it finishes instantly in a
    browser. The library's default is b = 32, and the numbers in this section use that.

  
Where to put the bound is a tradeoff. Drag it:

  

    
    

      
    

    

    

  

  
The default, 250,000, is about the mean plus one standard deviation: it rejects about 15% of
    salts, so a hash costs about 1.2 chains, or 230,000 iterations, including retries. A bound at
    the mean would reject half of all salts.


  
The stored string

  
The result records the salt and every parameter, in the style of the
    PHC string format, so
    verify needs only the password and this string:

  

    scheme$chip$
    hashh=sha256,
    bitsb=32,
    collisionsc=5,
    boundsmin=0,max=250000
    salt (base64)$SOXeJ7iDuFTAnzpA54YPoA
    final digest (base64)$jtbB33Sm…
  

  
To verify, CHIP reruns one chain with the stored salt and compares the result. No retries are
    needed, because the stored salt is the one that was accepted.

  
That creates a small asymmetry. The defender pays about 1.2 chains per hash
    because of retries. An attacker who stole the string knows the winning salt and pays exactly
    one chain per guess.

9. Attacks and limitations

  
CHIP makes each guess cost something, but less than it first appears, which
    is why Argon2id is the right choice in practice.


  
The time–memory tradeoff

  
Look at how the stored digests are used. All 200,000 are written, but a full digest is only
    ever read at a collision, and there are just C = 5 collisions per chain. Everything
    else only needs the low bits, to notice collisions.

  
So an attacker can keep just the iteration number at which each low-bit value first
    appeared, plus a full digest every 1,000 iterations as a checkpoint.
    When a collision needs Dj, they jump back to the nearest checkpoint before j and re-hash
    forward:

  

    
    

    

  

  
Each recovery costs half the checkpoint spacing on average, and there are only C of them.
    benchmarks/time_memory_tradeoff.py runs this and checks that the output is
    identical: at the defaults it costs about 1.3% more hashing and needs about 1.6 MB instead of
    6.4 MB. Try other spacings:

  

    
    

      
      
    

    

    

  

  
The saving levels off at about four times, because each stored value shrinks from a 32-byte
    digest to an 8-byte key and index. For short chains (b = 24) a spacing of 1,000 costs 19% more
    hashing, but an attacker would simply choose a smaller spacing. Argon2
    was designed to make tradeoffs like this expensive: it reads earlier memory at every step,
    not five times per run.


  
Parallelism

  
Separate guesses are independent, so an attacker can still run many at once. The waiting from
    section 2 is also easy to avoid, with two counter-moves:

  
    
    
  • Refill finished lanes. Every iteration of every guess does the same work
      (hash, take the low bits, look them up), so a lane that finishes can start the next guess
      right away while its neighbors carry on. Nothing waits.
    • 
    
  • Drop guesses past the upper bound. The right password always finishes
      within the bound stored in the hash string, so a chain that runs longer can't be the right
      one and can be abandoned.
    • 
  

  

    
    

    

      
      
      
    

  


  
Memory is small and tied to time

  
6.4 MB per guess is small next to current guidance:
    OWASP
    recommends at least 19 MiB for Argon2id, and RFC 9106
    recommends 64 MiB to 2 GiB. CHIP's memory also grows only with its iteration count, so it
    can't ask for more memory without also taking longer. At b = 34 and C = 30, about a million
    iterations, the digests take about 32 MB.


  
Iterations are modest

  
200,000 SHA-256 calls is less hashing than OWASP's recommendation for PBKDF2: 600,000
    iterations of HMAC-SHA256, each costing two SHA-256 compressions, about six times as much.


  
Side channels

  
CHIP's run time and memory access pattern depend on the password. Someone sharing the
    machine could learn something from timing or cache behavior. Argon2d has the same weakness;
    Argon2id was designed to reduce it.

10. Looking back from 2026

  
The ideas make good teaching material; a real design would decouple memory
    from time and read memory far more often.

  

  
I first built CHIP in 2018 and revisited it in 2026. What I'd keep:

  
    
    
  • Cost from the birthday bound. Two small integers give smooth,
      predictable control over the average cost, with a one-line formula behind it.
    • 
    
  • Building on SHA-256 rather than a new primitive, so the security of each
      step rests on a well-studied hash.
    • 
    
  • Self-describing hash strings, so parameters can change without breaking
      old hashes.
    • 
  

  
What I'd change:

  
    
    
  • Read memory more often. CHIP writes every digest but reads a full one only
      C times, which is why checkpoints make the memory cheap to avoid. Reading an earlier digest
      at every step, chosen by the data, would make each recovery expensive.
    • 
    
  • Set memory and time separately. Fill a memory region of chosen size first,
      then spend a chosen number of steps reading from it. That is essentially what scrypt and
      Argon2 do.
    • 
    
  • Don't count on variable run time. It costs the defender retries and
      side-channel exposure, and an attacker refilling lanes barely notices it.
    • 
  

  
For a real system, I'd use Argon2id.

  

  


  
  

  
Methodology

  
    
    
  • Every CHIP measurement on this page comes from a committed script in
      benchmarks/:
      iterations.py (1,000 chains for each b from 1 to 32 and C from 1 to 20),
      distribution.py (1,000 chains at the defaults, used by the lockstep and bound
      widgets), memory.py (100 chains per row), and
      time_memory_tradeoff.py (checks that the low-memory method gives identical
      hashes).
    • 
    
  • The step-through widgets hash with your browser's SHA-256 (WebCrypto), so they respond
      instantly. The chain widget's example chain is also pinned in the Python tests, so the two must agree. The demo at the top runs the actual Python library through
      Pyodide.
    • 
    
  • The tradeoff widget uses a simple model (half the spacing per recovery, 8 bytes per stored
      value); its caption compares it with the measured result.
    • 
    
  • Not measured here: real GPU attack throughput, a C implementation, or side channels.

Terms and references

  

    
Hash function, password hash

    
A hash function maps any input to a fixed-size output that is easy to compute and
      infeasible to reverse (SHA-256: 32 bytes). A password hash is a hash built to be slow and
      costly on purpose.

    
Digest

    
The output of one hash function call. CHIP's chain produces D1, D2, …

    
Salt

    
A random value (16 bytes in CHIP) stored with the hash and mixed into it, so equal
      passwords get different hashes and precomputed tables don't help.

    
Collision (in CHIP)

    
An iteration whose low b bits equal those of an earlier remembered digest. The full
      digests differ; only their low bits match.

    
Birthday bound

    
Among N equally likely values, the first repeat is expected after about √(πN/2) draws.
      Birthday problem.

    
XOR

    
Bitwise exclusive or: each output bit is 1 when exactly one input bit is 1. XOR with a
      random value scrambles every bit it touches.

    
Lockstep, warp

    
A GPU runs threads in groups (warps of 32 on NVIDIA hardware) that execute the same
      instruction together. A thread with nothing left to do waits for the rest of its warp.

    
Checkpoint, time–memory tradeoff

    
Keeping some intermediate values and recomputing the rest when needed, trading extra
      computation for less memory.

    
PBKDF2

    
Iterates HMAC many times; cost comes from iterations alone.
      RFC 8018.

    
bcrypt

    
Based on the Blowfish cipher's expensive key setup, with a small fixed memory (about 4 KB).
      Provos and Mazières, 1999.

    
scrypt

    
Fills a large memory region, then reads it back at data-dependent positions.
      RFC 7914.

    
Argon2 (Argon2d, Argon2i, Argon2id)

    
Winner of the Password Hashing Competition in 2015, with separate time, memory, and
      parallelism settings. Argon2id mixes data-independent and data-dependent memory access and
      is the recommended variant. RFC 9106.

    
PHC string format

    
A convention for self-describing hash strings: $scheme$params$salt$hash.
      Specification.
